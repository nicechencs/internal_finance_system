# 定期存款与账户管理关系评估及分阶段改动计划

状态：Active  
适用对象：产品 / 开发 / AI  
事实源级别：Secondary  
最后核对日期：2026-03-30

## 1. 背景

本文件用于记录以下结论与后续计划：

1. 定期存款管理页面与账户管理页面的业务关系。
2. 运行态联调后确认的问题与结论。
3. “更优方案建议”的必要性评估与改动量评估。
4. 推荐的详细改动方案与实施计划。

## 2. 当前结论

### 2.1 业务关系结论

当前系统中，`Account` 是账户主档，`FixedDepositRecord` 是定期业务记录。

更准确的业务关系应为：

`Account (FixedDeposit 类型账户) 1 -> N FixedDepositRecord`

也就是说：

1. 账户管理负责维护“定期账户主档”。
2. 定期存款页面负责维护“该定期账户下的定期记录台账”。
3. 定期记录不应被当作账户本身的固有属性，而应被视为账户下的子资源或业务台账。

### 2.2 运行态联调确认的问题

运行态验证后，已确认以下问题真实存在：

1. 账户详情页此前没有显式展示该账户下的定期记录，导致主从关系不可见。
2. 后端 `已到期 / Matured` 筛选与前端按到期日推导的状态不一致。
3. 定期台账页依赖“启用中的定期账户”来取数，导致定期账户停用后，其历史记录在台账页消失。
4. 页面命名与业务语义存在偏差，“定期存款管理”更接近“定期存款台账”。

### 2.3 本轮已完成的修复

本轮已经完成的低风险修复包括：

1. 统一后端 `Matured` 和 `Active` 的筛选口径。
2. 在账户详情页补充“定期记录”页签，显式展示账户下的定期记录。
3. 将定期页面命名收敛为“定期存款台账”。
4. 台账页不再依赖“仅启用账户”进行默认取数，停用账户的历史定期记录仍然可见。
5. 台账页支持从定期记录跳转到账户详情页。

### 2.4 本轮已执行的前端体验收口

在上述问题确认后，又继续落地了以下前端侧收口改动：

1. 新建 `FixedDeposit` 类型账户时，页面文案统一为“定期账户”，避免继续把“账户主档”和“定期记录”混为一谈。
2. 新建定期账户成功后，会弹出下一步引导，提示用户是否立即登记第一笔定期记录。
3. 若用户选择立即登记，系统会跳转到“定期存款台账”，自动带上 `accountId` 并直接打开新增定期记录弹窗。
4. 定期台账页支持读取路由意图参数：
   - `accountId`：自动筛选到账户
   - `action=create`：自动打开新增弹窗
5. 普通交易录入页不再默认展示定期账户，减少把定期资金流转误录为经营收支的概率。
6. 为兼容历史数据，编辑旧交易时如果原交易账户就是定期账户，当前账户仍可继续显示和编辑。
7. 转账、转为内部转账、定期支取等弹窗文案已统一强调：
   - 定期相关场景优先使用账户转账 / 内部转账 / 导入流水匹配
   - 不再把“手工新建定期支出交易”作为推荐路径
8. 定期账户详情页已增加“账户主档”说明卡，并将“定期记录”区域优先展示：
   - 无记录时提供“登记第一笔定期记录”入口
   - 明确说明账户创建只建立主档，真实本金 / 期限 / 利率需在定期记录中登记
9. 前端已完成构建验证：
   - 执行时间：2026-03-30
   - 命令：`npm.cmd run build`
   - 结果：通过

说明：

1. 本轮执行的是“前端交互收口”和“现有业务语义澄清”。
2. `Phase 1` 中“定期状态以后端为唯一真相源”与 `Phase 2A/2B` 的后端契约/数据库收口，仍属于后续阶段性工作，尚未在本轮全部展开。

## 3. 更优方案建议的综合评估

### 3.1 评估总表

| 建议 | 必要性 | 改动量 | 当前判断 | 推荐优先级 |
| --- | --- | --- | --- | --- |
| 定期状态以后端为唯一真相源 | 高 | 中 | 业务正确性问题，建议尽快收口 | P0 |
| 账户主档与定期台账彻底解耦 | 中高 | 中到大 | 架构必要，但建议分阶段落地 | P1 / P2 |
| 登录态启动优化 | 低到中 | 小 | 更偏体验优化，不是当前主线 | P3 |

### 3.2 建议一：定期状态以后端为唯一真相源

#### 必要性

高。

原因：

1. 这不是单纯的展示问题，而是业务口径不一致问题。
2. 后端现在已经修正了筛选逻辑，但 DTO 仍返回原始持久化状态，前端仍在多个页面自行按日期推导状态。
3. 只要状态解释权同时存在于前后端，后续仍可能再次出现“接口结果”和“页面显示”不一致。

#### 当前证据

1. 后端已通过 `ApplyStatusFilter` 修复筛选口径。
2. 但前端仍在以下位置自行派生状态：
   - `FixedDepositListPage.vue`
   - `AccountDetailPage.vue`
   - `FixedDepositWithdrawDialog.vue`

#### 改动量

中等。

主要改动集中在定期模块内部，边界清晰，属于高收益、可控范围内的重构。

#### 结论

建议作为下一阶段首要改动。

### 3.3 建议二：账户主档与定期台账彻底解耦

#### 必要性

中高。

原因：

1. `Account` 实体和 `AccountDto` 中仍保留一套账户级定期字段：
   - `InterestStartDate`
   - `MaturityDate`
   - `InterestRate`
   - `AutoRenewal`
2. `AccountService` 仍在创建和更新账户时读写这些字段。
3. `/account/maturing` 仍按账户级到期字段工作。
4. 这会让模型表达继续处于“双轨制”：
   - 一套在账户主档上
   - 一套在 `FixedDepositRecord` 上

这会让边界继续模糊，也会增加未来需求扩展和调试成本。

#### 当前证据

1. 开发库抽样结果：
   - `fixed_accounts = 2`
   - `accounts_with_legacy_fields = 0`
   - `fixed_accounts_without_records = 0`
2. 前端账户表单实际上已经不再提交这些定期字段。
3. 系统中的到期提醒当前已经优先使用 `fixed-deposits/maturing`，说明迁移方向已基本正确。

#### 改动量

中到大。

原因不是业务逻辑复杂，而是涉及层面更多：

1. 后端实体、DTO、Service、Controller。
2. 测试数据和历史接口契约。
3. 数据库字段是否最终物理删除。

#### 结论

建议分两阶段推进：

1. 先做代码与契约层收口。
2. 再做数据库物理清理。

### 3.4 建议三：登录态启动优化

#### 必要性

低到中。

原因：

1. 经过运行态验证，Cookie 会话本身是正常的。
2. 已登录后刷新受保护页面，登录态可以恢复。
3. 当前问题更像是“公共页或启动时机下的 `/auth/me` 探测会产生一次 401 噪音”，属于体验和联调质量问题。
4. 它不会改变定期存款与账户管理的核心业务关系。

#### 改动量

小。

主要影响前端路由守卫、用户 Store 和登录页启动逻辑。

#### 结论

建议后置处理，不应抢占业务模型修复优先级。

## 4. 推荐实施顺序

推荐按以下顺序执行：

1. Phase 1：统一定期状态口径。
2. Phase 2A：账户主档契约瘦身。
3. Phase 2B：数据库物理清理。
4. Phase 3：登录态启动优化。

推荐理由：

1. Phase 1 解决的是业务正确性问题。
2. Phase 2A 解决的是模型边界问题，能显著降低后续继续长歪的概率。
3. Phase 2B 属于结构收尾，应建立在代码层已经稳定的前提上。
4. Phase 3 更偏体验，不是本问题主线。

## 5. 详细改动方案

### 5.1 Phase 1：统一定期状态口径

#### 目标

让后端成为定期状态的唯一真相源，前端只消费后端返回的业务状态，不再自行派生。

#### 改动内容

1. 在后端新增或抽取模块内统一状态解析逻辑。
2. `FixedDepositDto` 返回派生后的业务状态，而不是单纯返回原始持久化状态。
3. 建议在 DTO 中补充以下字段：
   - `isOverdue`
   - `overdueDays`
   - 保留 `daysToMaturity` 表示未到期剩余天数
4. `FixedDepositService` 在以下场景统一复用同一套状态判定：
   - 列表筛选
   - 统计卡
   - DTO 映射
   - 到期提醒
5. 前端移除页面级 `dayjs + maturityDate` 的二次派生逻辑。
6. 页面状态标签、按钮禁用逻辑、剩余天数/逾期天数展示统一基于后端返回字段。

#### 预计影响范围

后端：

1. `FixedDepositService`
2. `FixedDepositDto`
3. 定期相关测试

前端：

1. `FixedDepositListPage.vue`
2. `AccountDetailPage.vue`
3. `FixedDepositWithdrawDialog.vue`
4. `fixedDeposit.ts`

#### 改动量评估

约 7 到 9 个文件，中等改动量。

#### 风险

1. 前端多个页面当前共享“自行派生状态”的旧逻辑，调整时需要一次性改干净。
2. 若 DTO 字段变更，相关类型和测试需要同步更新。

#### 验收标准

1. `/fixed-deposits?status=Matured`、统计卡、详情页、支取弹窗表现完全一致。
2. 前端不再存在对定期状态的日期二次派生逻辑。
3. 逾期记录在所有页面都展示为一致状态。

### 5.2 Phase 2A：账户主档契约瘦身

#### 目标

将账户主档收敛到账户基础属性，将定期业务属性全部收回到定期记录域。

#### 改动内容

1. 从以下账户层契约中移除定期业务字段：
   - `AccountDto`
   - `CreateAccountRequest`
   - `UpdateAccountRequest`
2. 从 `AccountService` 中移除这些字段的读写逻辑。
3. 前端 `Account` 类型同步移除旧字段，避免后续误用。
4. 对 `/account/maturing` 做处理：
   - 如需兼容，可先保留但标记废弃
   - 如确认无调用方，可直接删除
5. 测试中涉及“定期业务”的账户构造方式改为：
   - 创建 `FixedDeposit` 类型账户
   - 再创建 `FixedDepositRecord`

#### 预计影响范围

1. `Account` DTO 与请求模型
2. `AccountService`
3. `AccountController`
4. 前端账户类型定义
5. 若干后端单测、控制器测试、集成测试

#### 改动量评估

约 8 到 12 个文件，中等偏上的改动量。

#### 风险

1. 部分历史测试或调用方可能仍隐式依赖这些字段。
2. 需要确认是否有外部系统仍在调用 `/account/maturing`。

#### 验收标准

1. 账户 API 不再暴露定期业务字段。
2. 新建/编辑账户不再承载定期属性含义。
3. 系统内所有定期到期查询统一来自 `fixed-deposits` 域。

### 5.3 Phase 2B：数据库物理清理

#### 目标

删除 `accounts` 表上已经失去业务意义的账户级定期字段，完成真正的数据模型收口。

#### 改动内容

1. 先对正式环境做数据审计：
   - 是否存在 `fixeddeposit` 账户仍写有旧字段
   - 是否存在没有定期记录的定期账户
2. 若存在遗留数据，先做迁移脚本或补数方案。
3. 新增 Migration，移除：
   - `interest_start_date`
   - `maturity_date`
   - `interest_rate`
   - `auto_renewal`
   - 相关索引
4. 更新 EF 配置和快照，清理所有残留引用。

#### 改动量评估

约 3 到 5 个代码文件，加 1 个 Migration。

#### 风险

主要风险来自正式环境数据，而不是代码实现本身。

#### 验收标准

1. 数据库结构中不再保留账户级定期字段。
2. 新旧业务查询结果与 `Phase 2A` 保持一致。
3. 无测试或接口再依赖这些数据库列。

### 5.4 Phase 3：登录态启动优化

#### 目标

减少公共页或冷启动时 `/auth/me` 探测带来的 401 噪音，同时保持受保护页面的自动恢复能力。

#### 改动内容

1. 路由守卫区分公共页和受保护页：
   - 受保护页仍执行 `bootstrapSession`
   - 公共页不默认探测
2. 登录成功后写入一个非敏感本地提示位，例如 `sessionStorage.auth_seen = 1`。
3. 登录页仅在存在提示位时才尝试探测当前登录态。
4. 退出登录时清理提示位。
5. 保持现有 Cookie 会话机制不变。

#### 改动量评估

约 4 到 5 个文件，小改动。

#### 风险

1. 若处理不当，可能影响“已登录用户访问登录页自动跳回首页”的体验。
2. 需要确认受保护页首屏初始化流程不被破坏。

#### 验收标准

1. 直接打开 `/login` 不再产生无意义的 `/auth/me` 请求。
2. 已登录用户刷新受保护页仍可恢复会话。
3. 已登录用户访问 `/login` 仍能正确跳转回首页。

## 6. 推荐执行包

如果只选择一轮连续实施，推荐执行：

`Phase 1 + Phase 2A`

原因：

1. 它们共同解决“口径不一致”和“模型边界不清”两个核心问题。
2. 这两步做完后，业务语义会明显稳定。
3. 后续数据库清理和登录态优化都能转为低风险收尾项。

## 7. 暂不建议本轮直接做的事项

以下事项不建议和当前业务修复绑成一轮大改：

1. 立即删除数据库字段而不做正式环境数据审计。
2. 在同一轮里同时大改定期状态、账户契约、数据库结构、登录态启动逻辑。
3. 把登录态体验优化提升为高优先级，挤占业务模型修复资源。

## 8. 后续讨论建议

后续若继续讨论，建议优先围绕以下问题展开：

1. Phase 1 是否直接开始实施。
2. `/account/maturing` 是否需要兼容保留一个版本周期。
3. 正式环境是否允许执行账户级旧字段的数据审计。
4. Phase 2A 和 Phase 2B 是否分两个迭代发布。
