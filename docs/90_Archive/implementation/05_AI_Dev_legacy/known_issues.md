# 已知问题与使用限制

本文档记录系统中已知的使用问题、限制及建议操作顺序，供开发和运维参考。

---

## KI-001 · 先导入流水再创建关联信息时，关联字段无法跳转

**模块**：交易记录 / 银行流水导入 / 项目管理

**现象**：

交易记录详情页中，对方名称、对方账户、对方银行、所属项目等字段在正常情况下支持点击跳转（关联至客户、供应商、项目等详情页面）。但若操作顺序为：

1. 先导入银行流水（此时对方信息或项目尚未在系统中创建）
2. 事后在系统中创建对应的对方信息（客户/供应商等）或项目

则已导入的交易记录中，上述字段的跳转链接不会自动建立，仍显示为纯文本，无法点击跳转。

**影响范围**：

- 对方信息（客户、供应商、人员）：先导入后创建时，`customer_id`、`supplier_id`、`person_id` 等外键不会回填；客户管理、供应商管理、人员管理详情页中的"相关交易"列表也无法展示这些历史记录
- 项目信息：先导入后创建项目时，`project_id` 外键不会回填，项目详情页中的关联交易记录同样缺失
- 账户管理：若导入时使用了系统中尚不存在的账户，`account_id` 外键同样无法建立，账户详情页的流水记录会出现缺失

**根本原因**：

银行流水导入时，对方名称、项目名称等字段以文本形式写入 `bank_statements` 及 `transactions` 表。关联关系（外键）在导入阶段通过名称匹配规则引擎建立；若关联信息在导入后才创建，历史交易记录的外键字段不会被回填。

**建议操作顺序**：

> 先维护基础数据，再导入银行流水。
>
> 1. 在系统中录入客户、供应商、人员等对方信息
> 2. 创建项目信息
> 3. 配置分类规则（可选）
> 4. 导入银行流水 Excel
>
> 按此顺序操作，规则引擎可在导入时自动匹配并建立关联，所有字段跳转功能正常。

**临时解决方案**：

对于已导入但未建立关联的历史交易记录，可通过以下方式手动修复：

- 在交易记录详情页手动编辑，重新选择正确的对方信息或项目
- 或由开发人员执行数据库脚本，批量回填外键关联（需根据名称匹配，存在一定风险，请谨慎操作）

**后续优化方向**（待排期）：

- **一键关联功能**：在交易记录列表或对方信息/项目详情页提供"一键关联"按钮，触发后系统自动按名称匹配历史记录并回填外键，支持预览匹配结果后确认执行
- 或在导入流程结束后提供"未匹配记录"列表，允许用户逐条或批量手动指定关联
- 新增信息创建后自动触发历史回填的后台任务（需注意重名歧义，参见 KI-002）

## KI-002 · 对方名称重名时的匹配歧义问题

**模块**：交易记录 / 银行流水导入 / 规则引擎

**现象**：

当系统中存在两个或多个名称相同的对方信息（例如：两个名为"张三"的客户，或客户与供应商中各有一个"XX贸易"），银行流水导入时，规则引擎按名称匹配无法确定应关联哪一条记录，可能出现以下情况：

- 匹配到错误的对方信息（关联至不相关的客户/供应商）
- 匹配失败，对方字段保持纯文本，跳转链接不建立

**根本原因**：

规则引擎以对方名称作为匹配键，未区分同名对方的身份（如所属类型、账户信息、联系方式等）。名称重复时，匹配结果不确定。

**风险等级**：中等

重名匹配错误会导致交易记录关联到错误的对方，影响应收应付统计及对账准确性，但不会造成数据丢失。

**建议处理方式**：

1. **录入时区分命名**：建议在系统中为同名对方添加区分标识，例如：
   - "张三（北京）" / "张三（上海）"
   - "XX贸易-客户" / "XX贸易-供应商"

2. **结合账户信息辅助区分**：在对方信息中尽量填写银行账号，导入时可通过账号进行二次匹配，准确率高于纯名称匹配。

3. **导入后人工核查**：对于可能存在重名的批次，导入完成后建议筛选相关交易记录，逐条核实对方关联是否正确。

4. **手动修正**：若发现关联错误，可在交易记录详情页手动重新选择正确的对方信息。

**后续优化方向**（待排期）：

- 导入时检测名称重复并给出警告提示，要求用户手动指定
- 增加多维度匹配策略（名称 + 账号 + 开户行），降低单一名称匹配的歧义概率
- 提供"疑似重名对方"管理页面，帮助用户提前发现并处理重名问题

## KI-003 · 账户列表与账户详情中"开户行"字段名称不一致

**模块**：账户管理

**现象**：

账户详情页中，银行名称字段显示为"开户行"；但在账户管理列表页的对应列中，该字段的列标题名称与详情页不一致（未对齐统一）。

**影响**：

纯 UI 展示问题，不影响数据正确性，但会造成用户认知混乱，降低界面一致性。

**后续优化方向**：

统一前端各处对该字段的显示名称，建议以"开户行"为准，同步修改列表列标题、表单标签、搜索筛选项等所有出现该字段的位置。

## KI-004 · 所有列表表格缺少表头排序功能

**模块**：全局（所有列表页）

**现象**：

系统中各模块的列表表格（交易记录、账户、客户、供应商、应收应付等）目前均不支持点击表头进行排序，用户无法按日期、金额、名称等字段自定义排列顺序。

**期望行为**：

点击表头字段（如"日期"、"金额"、"创建时间"等）时，应支持升序 / 降序 / 默认三态切换，并同步刷新列表数据。

**后续优化方向**：

- Element Plus `el-table` 的列组件原生支持 `sortable` 属性，优先级较高的字段（如日期、金额）建议设为 `sortable="custom"`，由后端接收排序参数后返回有序数据，避免仅对当前分页数据排序导致结果不准确
- 后端各列表接口统一增加 `sortBy` / `sortOrder` 查询参数支持
- 建议优先实现：交易记录（按日期、金额）、应收应付（按到期日、金额）

## KI-005 · Excel 导入时"交易描述"与"摘要"字段被合并，且凭证号码未被记录

**模块**：银行流水导入 / 交易记录

**现象**：

Excel 流水文件中存在以下字段，但导入后出现以下问题：

1. **"交易描述"与"摘要"被合并**：两个字段在导入后未分别存储，而是被合并写入同一字段。这两个字段记录的是不同维度的信息（交易描述为银行系统生成的交易类型说明，摘要为用户或对方填写的备注内容），不应合并。

2. **凭证号码未记录**：Excel 中的凭证号码字段在导入过程中被忽略，未写入数据库，导致后续无法通过凭证号码追溯原始凭证。

**影响**：

- 合并字段导致原始信息丢失，影响对账和数据追溯
- 凭证号码缺失，无法与线下凭证或银行回单进行匹配核对

**后续优化方向**（待排期）：

- 数据库 `bank_statements` 表需新增字段：
  - `description`：交易描述（银行系统生成）
  - `summary`：摘要（对方/用户填写的备注）
  - `voucher_no`：凭证号码
- 同步更新 Excel 解析逻辑，分别读取并写入上述三个字段
- `transactions` 表视情况同步扩展，确保交易记录中也能查看完整的原始凭证信息

## KI-006 · 导入后新增规则，历史交易记录不会自动重新分类

**模块**：交易记录 / 规则引擎

**现象**：

银行流水导入时，规则引擎会对每条记录执行一次分类匹配，将匹配结果写入 `category_id` 等字段。若导入完成后再新增或修改分类规则，已导入的历史交易记录**不会自动触发重新匹配**，其分类信息保持导入时的状态不变（可能为空或旧分类）。

**影响**：

- 新规则只对后续新导入的数据生效
- 历史记录的分类字段可能为空（未分类）或与新规则不符，影响报表统计准确性

**后续优化方向**（待排期）：

- 提供"规则重跑"功能：针对指定时间范围或全部历史记录，手动触发规则引擎重新执行分类匹配
- 规则重跑时需处理冲突策略：
  - 仅回填空白分类（保守策略，不覆盖已有分类）
  - 全量覆盖（激进策略，按最新规则重新分类所有记录）
  - 建议默认采用保守策略，并提供选项让用户自行决定
- 新增或修改规则后，界面给出提示："已有 X 条历史记录可能受此规则影响，是否立即重新匹配？"

## KI-007 · 应收应付管理页面无数据时图表仍显示数据

**模块**：应收应付管理 / 图表可视化

**现象**：

应收应付管理页面在实际无业务数据的情况下，"应收应付趋势"和"账龄分析"两个图表仍然渲染出数据，而非显示空状态（如"暂无数据"占位）。

**可能原因**：

1. **图表使用了硬编码的 Mock 数据**：组件开发阶段遗留的演示数据未清除，导致接口返回空时仍走本地 fallback 数据渲染
2. **接口返回空数组时未判断**：图表初始化逻辑未区分"接口尚未返回"与"接口返回空数据"两种状态，直接使用了初始化默认值渲染
3. **ECharts 配置项含默认数据**：图表 option 中的 `series.data` 存在默认占位值，未在数据加载后清空

**影响**：

误导用户，显示虚假数据，影响判断。

**修复方向**：

- 检查图表组件，移除所有 Mock / 硬编码的演示数据
- 接口返回空数组或 null 时，图表应切换至空状态展示（可使用 ECharts 的 `graphic` 配置或外层条件渲染实现）
- 建议统一约定：图表组件在 `data.length === 0` 时显示"暂无数据"文字占位，不渲染坐标轴和折线

## KI-008 · 疑问：流水导入批次历史记录是否可查？

**模块**：银行流水导入

**问题描述**：

当前导入页面支持上传 Excel 并执行导入，但存在以下待确认问题：

1. **历史批次是否保留**：每次导入操作是否会记录一条导入批次记录（如导入时间、导入人、文件名、导入条数、成功/失败数）？还是导入完成后批次信息即丢弃，只保留导入的流水明细？

2. **是否可查看导入历史列表**：用户能否在导入页面查看历次导入批次的列表（类似"导入记录"Tab）？

3. **是否可查看单次导入详情**：点击某一历史批次后，能否查看该次导入的具体明细，包括：成功写入的记录、因重复被跳过的记录、解析失败的记录？

**当前判断**：

系统存在 `bank_statements` 表记录流水明细，但目前 **不确定是否存在独立的导入批次表**（如 `import_batches`）来追踪每次导入操作的元信息。若无此表，则历史批次信息不可查。

**后续优化方向**（待排期）：

- 确认数据库中是否已有 `import_batches` 或类似批次追踪表
- 若无，建议新增，字段包括：`id`、`file_name`、`imported_by`、`imported_at`、`total_rows`、`success_count`、`duplicate_count`、`fail_count`、`status`
- 前端导入页面增加"导入历史"入口，支持查看历次批次列表及单次详情（含成功/重复/失败明细分组展示）
