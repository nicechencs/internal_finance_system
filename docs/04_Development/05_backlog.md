## 高优先级

- 人员交付 / 验收记录功能：人员模块增加交付物、验收状态、验收时间和关联项目记录。
- 凭证号（`voucher_no`）功能评估与实施：确认业务口径、导入映射、交易表单展示和查询筛选需求。

## 中优先级

- 各模块列表排序能力统一：补齐仍缺少表头排序或后端排序参数的列表。
- 账户模块“开户行 / 银行名称”命名统一：统一列表、详情、表单、筛选项和导入字段文案。
- 前端独立报表页接入：后端报表接口和前端 API 已存在，仍需页面与路由入口。
- 账户关联分支支持：补齐 LinkService 中账户关联能力。
- 标签规则扩展到非交易作用域：评估项目、人员、客户、供应商等标签作用域的自动规则。
- 标签每日汇总快照闭环：补齐生成任务、查询 API 和前端消费。
- 应收 / 应付服务重复逻辑提取：在不改变行为的前提下提炼共用查询、状态计算和标签装配逻辑。

## 低优先级

- API 自动类型生成：评估 `swagger-typescript-api` 或等价工具，减少前端手写接口类型。
- 前端 chunk 优化：按路由和重型图表组件拆包，降低主包体积。
- 报表读模型优化：为仪表盘、项目利润、现金流等高频统计评估缓存或读模型。当前已先做 SQL 聚合下推，见 [性能优化方案](08_performance_optimization_plan.md)；缓存 / 读模型仍待评估。

## 架构优化（Phase 2+）

- Phase 2：收紧后端边界，逐步废弃 Application 层直接使用 `GetQueryable()`。
- Phase 3：继续拆分前端大页面，把复杂业务逻辑沉入 feature 内部组件和 composable。
- Phase 4：治理横切能力，剥离 request 层 UI 副作用，收口会话、权限和审计链路。
- Phase 5：沉淀领域规则，提炼交易、转账、分摊、应收应付状态流转不变量。
